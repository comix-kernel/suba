# Comix 教学内核架构综述

这份综述沿着启动和文件访问过程介绍教学内核。[裁剪与重构设计](teaching_kernel_design.md)按需求、参考机制、整体架构和模块实现展开，并给出任务状态文件和服务组合的验收用例。

## Comix 要解决什么问题

Comix 的目标是把一个能够运行 Linux 程序的实验内核，裁剪成一个能在数千行源码内讲清楚的双核教学系统。它需要保留操作系统承担的基本职责，包括接管机器、管理内存、分配 CPU、驱动设备和协调并发活动。学生应当能沿着源码追踪资源的授权过程、任务等待期间的调度过程，以及服务更新在另一个核上的可见时刻。

现有 Comix 的许多代码来自兼容性要求。启动第一个程序需要探测分区、挂载 ext4，再按路径装载用户态 ELF。创建子任务时，内核还要处理 Linux 线程、信号、文件描述符和地址空间的多种共享方式。这些机制对运行现成软件有价值，却让启动一个任务或唤醒一个等待者都牵涉多个子系统。仅删除几个文件系统和驱动，任务、内存与 I/O 之间的依赖仍然存在。[现有启动路径](https://github.com/comix-kernel/comix/blob/e2dc94bcb05d85e5748a2717af8d87714195eae1/os/src/kernel/boot.rs#L203) · [现有任务创建路径](https://github.com/comix-kernel/comix/blob/e2dc94bcb05d85e5748a2717af8d87714195eae1/os/src/kernel/syscall/task/clone_ops.rs)

为缩小内核规模，教学版本重新定义程序的执行方式、资源接口和跨核共享状态的范围。首版面向 RISC-V 双核机器和随镜像构建的 Rust 组件。这个范围允许 Comix 去掉 Linux ABI、磁盘根文件系统和网络栈，同时保留硬件中断、时间片抢占、阻塞唤醒和真实的跨核竞争。以下架构是拟议设计。

## 第一版机器上实际运行什么

构建系统把运行时、驱动、服务和 shell 链接成一个 RISC-V 内核镜像。启动时只有一张页表，所有 Comix 代码都在 S 态执行。镜像里有两类入口。分配内存、创建任务、收发消息是可以直接调用的运行时函数。shell、管理任务及各个服务有各自的任务入口，每个入口获得独立的栈和一组启动参数，由调度器分配 CPU 时间。

下面是一种双核演示布局。图中的任务固定在指定核上，各核按时间片轮流执行就绪任务。

```text
                         同一个内核镜像，共享一张页表
              核 0                                  核 1
       ┌─────────────────┐                  ┌─────────────────┐
       │ 管理任务          │                  │ shell 任务       │
       │ 串口服务任务      │                  │ 内存文件服务任务  │
       ├─────────────────┤                  ├─────────────────┤
       │ 就绪队列 0        │                  │ 就绪队列 1       │
       │ 服务目录副本 0    │                  │ 服务目录副本 1   │
       └─────────────────┘                  └─────────────────┘
           公用设施    内存分配器、消息队列实现、服务实例表、目录操作日志
```

### 从现有启动代码改起

当前 `run_primary_boot` 在安装页表和中断后调用 `rest_init`。随后 PID 1 创建 `kthreadd`，探测 ext4 根分区，配置网络，最后执行 `kernel_execve("/sbin/init", …)`。教学版本沿用 RV64 的高地址入口、页帧分配和 SBI 从核启动，在双核就绪后把第一个可运行任务改成 `manager_main`。下面是拟议启动接口的伪代码。[当前启动入口](https://github.com/comix-kernel/comix/blob/e2dc94bcb05d85e5748a2717af8d87714195eae1/os/src/kernel/boot.rs#L103)

```text
manager_main(uart, registry):
    cons = start_service(hart=0, entry=console_main, device=uart)
    mem  = start_service(hart=1, entry=memfs_v1_main, state=empty_store())
    wait_ready(cons, mem)
    registry.publish("console", cons.id)
    registry.publish("store", mem.id)
    ns = namespace({"/dev": "console", "/work": "store"})
    spawn(hart=1, entry=shell_main, argument=ns)
    serve_admin_requests()
```

`start_service` 创建一对端点，把唯一的接收端交给新任务，把发送端保存在实例表里，再将任务加入所属核的就绪队列。服务建好自己的状态后发出就绪通知。此时进程式的父子关系已经可以去掉。创建者得到实例句柄，调度器只持有任务标识、所属核、状态、栈和寄存器上下文。目录记录只含服务名、实例身份和版本。

### 一个任务第一次怎样得到 CPU

现有 `kthread_spawn` 创建一个内核线程也会从当前任务复制信号、资源限额和文件描述符表。教学版的 `spawn` 只申请栈槽，保存一次性入口及其参数，把初始 `sp` 设到对齐后的栈顶，`ra` 设为统一的 `task_start`。既有的 `switch.S` 恢复 `ra/sp/s0–s11` 并执行 `ret`，第一次切入就到达 `task_start`。它从当前任务中取走入口并执行，入口返回后交回调度器，由调度器在另一张栈上回收栈槽。[当前内核线程创建](https://github.com/comix-kernel/comix/blob/e2dc94bcb05d85e5748a2717af8d87714195eae1/os/src/kernel/task/ktask.rs#L37) · [切换汇编](https://github.com/comix-kernel/comix/blob/e2dc94bcb05d85e5748a2717af8d87714195eae1/os/src/arch/riscv/kernel/switch.S)

时钟可以打断任意指令，现场还包含临时寄存器、`sepc` 和 `sstatus`。现有陷入汇编假定 `sscratch` 指向当前任务的 trap frame。教学版拟把 S 态中断现场直接压在被打断任务的栈上，`tp` 始终指向本核控制块。调度器切走后，任务下次恢复时从原栈恢复现场并执行 `sret`。切换汇编可以沿用，陷入入口和 `Cpu::switch_task` 需要一起改，后者目前还负责更新页表与 `sscratch`。[现有陷入约定](https://github.com/comix-kernel/comix/blob/e2dc94bcb05d85e5748a2717af8d87714195eae1/os/src/arch/riscv/trap/trap_entry.S#L10) · [当前任务切换](https://github.com/comix-kernel/comix/blob/e2dc94bcb05d85e5748a2717af8d87714195eae1/os/src/kernel/cpu.rs#L90)

## 为什么选择 Theseus、Plan 9 和 NrOS

### Theseus 把执行边界交给语言和模块

当所有应用都可以由项目控制工具链和源代码时，内核可以利用 Rust 表达资源的所有权。Theseus 将应用和内核组件放入同一虚拟地址空间，以同一特权级运行，并在运行时保留组件边界。它尤其关注一项状态由谁持有。一个组件越少代替其他组件保存内部状态，替换它时需要协调的依赖就越少。[Theseus 论文](https://www.usenix.org/conference/osdi20/presentation/boos)

Comix 拟让内核、服务和应用共用一张 Sv39 页表，在 S 态执行。每个任务仍有独立的栈和调度上下文。运行时创建任务时交给它一个 Rust 入口和一组初始句柄。启动代码可以把唯一的设备句柄移交给驱动，普通组件只能调用自己持有的安全接口。这样，任务切换保留了寄存器保存与恢复，资源权限则能从类型和构造函数中读出来。相应的代价是，底层驱动中的错误裸指针可能影响整机，平台和内存模块中的不安全代码必须集中审查。

首版把可替换的两个实现预先链接进镜像。服务实例拥有自己的队列和业务数据，管理任务可以启动另一个实现，决定何时接入新客户端、何时回收旧实例。这足以讲解运行时替换和状态迁移，也明确了它与 Theseus 完整动态装载机制的范围差异。

### Plan 9 为独立组件提供共同的资源接口

语言可以约束组件持有什么，却不会替系统决定应用怎样发现资源，也不会自动消除应用对具体驱动的依赖。Plan 9 让服务导出文件树，让每个进程通过自己的命名空间组合这些树，再用 9P 请求访问其中的资源。这个设计把路径的解释权交给客户端，把资源行为交给服务端。[Plan 9 设计原文](https://9p.io/sys/doc/9.html)

Comix 采用文件树、任务私有命名空间和请求／回复语义。首版用有界的本机队列传递 Rust 消息。任务共享地址空间，仍然可能以不同速度运行，队列明确了缓冲区由谁持有、容量用尽时谁等待，以及谁负责回复。应用依赖服务协议，服务实现可以独立改变。页帧分配、中断处理和调度继续使用直接的 Rust 调用，以保证机器能在第一个服务启动之前完成初始化。

### NrOS 让跨核共享有明确的顺序

任务可以拥有各自的命名空间，两个核则需要对已发布服务名所指向的实例取得一致意见。如果每个核单独修改自己的目录，其他核可能继续接入已退役的实例。NrOS 将共享对象写成顺序状态机，由复制层合并写操作、追加有序日志并驱动各副本按序执行。读取方先让本地副本追到规定的位置，再查询本地状态。原系统以 NUMA 节点为复制单位。[NrOS 论文](https://www.usenix.org/conference/osdi21/presentation/bhardwaj)

Comix 选择服务目录作为第一个复制对象，每个核保存一份。目录只有名称、实例身份和版本，发布与撤销都能写成确定性的更新。两个核从同一初始目录重放同一批记录，便能分别算出相同的结果。这种选择保留了多核一致性的实质，也限定了复制成本。慢副本会占用日志空间，新的发布可能需要等待。任务栈、服务的业务数据和设备寄存器各有所有者，目录重放只改变名称记录。

## 三种设计如何组成一个内核

两核可以持有相同的实例身份，接收请求的队列始终只有一条。以 `store` 的一次并存切换为例，下表假设服务允许新旧版本的数据独立演进。`A`、`B` 是两个实例，`h` 是客户端已经取得的连接。新旧实现均已链接进镜像。

| 时刻 | 实例管理器 | 核 1 看到的目录 | 客户端动作 |
| --- | --- | --- | --- |
| 发布前 | A 接收连接。B 正在初始化 | `store → (A, 7)` | `h` 持有 A 的发送端 |
| B 就绪 | 管理器锁住 `store` 的接入入口，提交“预期 A/7，替换为 B/8” | 查询开始时先追到当时已发布的日志末端 | 已取得 `h` 的任务仍可向 A 发送请求 |
| 提交成功 | 在接入锁下把 A 标为退役、开放 B，随后解锁 | 更新发布后开始的查询得到 `store → (B, 8)` | 新连接取得 B 的发送端。此前查询到 A 却尚未取得引用的客户端在接入时重新查询 |
| 旧请求结束 | A 的连接、在途回复和回调全部释放后，管理器停止 A 并回收其任务 | 目录仍指向 B | `h` 关闭只影响 A，B 继续运行 |

这里有三个可独立观察的动作。`spawn(memfs_v2_main)` 只创建任务。重放目录日志只改名称记录。从实例队列取出 `Write` 才会修改文件内容。将串口计数或文件追加放入日志重放函数，会让两个副本各执行一次副作用。若业务要求 A 与 B 接续同一份可写数据，管理器改用静止迁移流程，最后一节给出该情形。

这种划分也给维护工作划出了范围。把 UART 轮询改成中断接收，主要改动在板级驱动和就绪通知。升级内存服务的数据格式，需要修改快照导入和校验。调整目录日志的容量，则需要重新检验慢副本和日志回绕。每项改动都能找到具体的数据所有者和对应的验收场景。模块边界、源码取舍与分阶段验收见[教学内核裁剪与重构设计](teaching_kernel_design.md)。

## 两个任务打开同一路径的例子

两个任务运行相同的输出程序，都打开 `/dev/cons`。第一个任务把串口服务挂到自己的 `/dev`，第二个任务把记录服务挂到同一位置。两个服务各自导出名为 `cons` 的文件。客户端先按任务的挂载视图确定服务名，再从本核目录查到实例，并向它请求打开文件。随后两个任务写入同一行文字，一份出现在串口，另一份保存在记录服务中。

此时，核 0 上的管理任务尝试把记录服务从版本 7 升到版本 8。如果记录文件要保留完整历史，而第二个任务仍持有可写连接，升级返回忙。待它写完并关闭连接，旧实例导出内容和修订号，新实例校验并接续这份状态，管理任务才发布版本 8。核 1 上的任务随后重新打开同一路径时，它的目录副本先追平发布记录，连接由此指向版本 8。复制过程不会再次追加那行文字，串口任务也可以始终沿自己的连接继续输出。
