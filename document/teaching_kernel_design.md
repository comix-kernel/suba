# Comix 教学内核裁剪与重构设计

本文以 Comix 提交 `e2dc94b` 为基线，描述拟实施的教学版本。目标平台为 QEMU `virt`、RV64、OpenSBI、128 MiB 内存。验收使用两个 hart（RISC-V 硬件线程）。固件运行在 M 态，Comix 内核、服务和应用全部运行在 S 态，共用一张 Sv39 根页表。

当前源码、早期演示实现的差距及验收入口见[架构对照与实现](teaching_kernel_implementation.md#架构对照与实现)。规模目标为数千行，Make 验收报告实测行数。

## 一、需求与关键机制

读者应能沿着一次文件操作找到三样东西：哪个服务解释这个对象，谁持有修改它的权利，另一个核从何时起能看到修改。服务可以同时作为其他服务的客户端。这让组合具有可观察的含义：即使应用只打开一个文件，请求也可以依次经过两个独立实现。

| 需求 | 首版如何实现 | 能判定设计成立的现象 |
| --- | --- | --- |
| 用文件呈现内核对象 | 服务将对象导出为树中的节点；任务通过私有挂载视图选择服务，以连接内的 fid 访问节点 | 同一段读取代码既能读内存文件，也能分段读完某个任务的一次状态快照 |
| 组合实现，控制依赖 | 构造服务时移入下游文件句柄或唯一设备令牌；服务可对上游导出文件，并通过持有的句柄调用下游 | 在输出程序与 UART 之间插入计数服务，只改启动组装；短写时计数与实际确认的字节数相同 |
| 在系统运行时替换实现 | 新实例先就绪，管理器按预期版本切换名称；连接固定实例，可写业务状态通过静止快照交接 | 旧连接能完成请求，新连接进入新版；快照校验失败时旧版仍可接入，内容和修订号完整 |
| 减少必须同时推理的并发行为 | 服务任务独占业务对象，调度状态归所属核；需要全局一致的服务名绑定用顺序函数和有序日志更新 | 用同一旧版本竞争替换，两个核对胜者达成一致；慢副本追赶时，串口输出字节数保持原值 |
| 内核可通读、可维护 | 单一 RV64 教学配置，分阶段解除用户 ELF、制盘和网络依赖；每个模块给出状态所有者、失败边界和验收入口 | 无盘双核能进入 shell；能从一次挂起的文件请求定位其任务、队列、服务实例和等待条件 |

规模目标是数千行。8,000 行自有运行代码是本稿用于约束首版的预算建议。双核、预链接组件、复制服务目录也是具体实现选择。教学验收关注上表中的可观察行为。[需求交接](teaching_kernel_requirements.md)

### Plan 9：从服务入口到内核对象

Plan 9 将发布、命名和访问分成三步。发布者向 `/srv` 的条目写入 fd，`srvwrite` 取得相应的 `Chan` 引用，另一进程打开条目时，`srvopen` 检查权限并返回该通道的引用。路径遍历时，`findmount` 从当前进程的 `Pgrp` 查挂载表，遇到挂载点才转到目标通道。于是一个服务可被不同进程挂到不同位置。Comix 让挂载表存储服务名，并把**每次新建连接**作为选择版本的时刻，已有连接持有原实例。这是 Comix 为运行时替换增加的间接寻址。[Plan 9 设计原文](https://9p.io/sys/doc/9.html) · [端点的发布和取得](https://github.com/plan9foundation/plan9/blob/ed1a9c21e3297d7497a48053d33683375c75fbb4/sys/src/9/port/devsrv.c#L104) · [按进程组解析挂载点](https://github.com/plan9foundation/plan9/blob/ed1a9c21e3297d7497a48053d33683375c75fbb4/sys/src/9/port/chan.c#L855)

服务端的 `sattach` 建立根 fid，`swalk` 查旧 fid 并准备目标 fid，`sclunk` 释放 fid。客户端的 `mountmux` 按 tag 找到在途请求，允许不同请求的回复交错。内核对象也能实现这一套文件语义：Plan 9 的进程设备按槽号找到进程，再核对 pid，避免槽位复用后读到另一个进程的状态。Comix 用带类型的本机消息保留这两种身份及其寿命，任务状态服务则在打开时取快照。首版将多分量 Walk 定义为全部成功才产生目标 fid，省去 9P 的部分遍历结果和线编码。[lib9p 的 fid 管理](https://github.com/plan9foundation/plan9/blob/ed1a9c21e3297d7497a48053d33683375c75fbb4/sys/src/lib9p/srv.c#L300) · [按 tag 匹配回复](https://github.com/plan9foundation/plan9/blob/ed1a9c21e3297d7497a48053d33683375c75fbb4/sys/src/9/port/devmnt.c#L934) · [进程状态读取](https://github.com/plan9foundation/plan9/blob/ed1a9c21e3297d7497a48053d33683375c75fbb4/sys/src/9/port/devproc.c#L716)

### Theseus：替换时必须找到哪些依赖

Theseus 论文把组件替其他组件长期保管的内部状态称为 *state spill*。源码中可以看到依赖如何影响替换粒度：应用装载器在选定的 crate 命名空间解析入口，把应用 crate 引用和命名空间交给新任务。替换器遍历旧 crate 的公开段及依赖这些段的重定位项，改写目标地址，更新依赖记录。它有复制对应数据段的路径，也允许显式调用状态迁移函数。这解释了为什么旧 crate 从命名空间移除后，仍可能有运行中的任务持有它。[Theseus 论文，第 3–6 节](https://www.usenix.org/conference/osdi20/presentation/boos) · [应用任务持有装载引用](https://github.com/theseus-os/Theseus/blob/1fbfe567075a65ed749b6680db1aeb538819c70c/kernel/spawn/src/lib.rs#L215) · [跟踪段依赖](https://github.com/theseus-os/Theseus/blob/1fbfe567075a65ed749b6680db1aeb538819c70c/kernel/crate_swap/src/lib.rs#L316) · [调用迁移函数](https://github.com/theseus-os/Theseus/blob/1fbfe567075a65ed749b6680db1aeb538819c70c/kernel/crate_swap/src/lib.rs#L505)

Comix 将运行时替换的边界定在文件服务实例。调用者只能持有连接，服务独占其 fid 表和业务数据。两个实现都链接进同一镜像，切换只需改变一个服务名的绑定。旧连接自然标出仍依赖旧实现的调用者。稳定契约包括导出路径、打开模式、读写效果和错误含义；Rust 类型检查负责消息与资源的交接，两版服务共用的契约测试负责检查行为。快照模式版本、目录发布代号和文件内容修订号分别描述格式、实例绑定和业务更新，三者独立演进。

### NrOS：先写顺序规格，再决定复制什么

NrOS 的 `KernelNode` 把进程分配和核分配表示为写操作，将“指定核上的当前进程”表示为查询。业务规则在 `dispatch_mut` 和 `dispatch` 中以顺序代码实现。该版本引用的复制库先收集发起线程的待办操作，由合并者成批追加日志，再按序执行，并将结果分发给本副本的发起线程。读操作采样已完成的日志位置 `ctail`，本地副本追到该位置才查询。环形日志需要等最慢副本越过旧记录才能复用槽位。[NrOS 论文，第 2、4 节](https://www.usenix.org/conference/osdi21/presentation/bhardwaj) · [内核顺序对象](https://github.com/vmware-archive/node-replicated-kernel/blob/38557a67be10c249853300560cc7e1d09f90c8aa/kernel/src/nr.rs#L171) · [读取与合并](https://github.com/gz/node-replication/blob/c90bf138faebd09aa51e629650fdf7d026dd1331/nr/src/replica.rs#L504) · [日志回收](https://github.com/gz/node-replication/blob/c90bf138faebd09aa51e629650fdf7d026dd1331/nr/src/log.rs#L536)

Comix 首先给每个可变对象找一个所有者。UART 字节只由串口服务写出，任务只由所属核调度。两个核都要发现当前服务，因而选择**服务名到实例的绑定**作为首个复制对象。先在单个普通目录上定义条件更新，再在两个核上用同一日志驱动这段代码。双核教学实现用短锁一次公布完整批次，读者以已发布末端为追赶目标。这样把并发推理集中在日志、接入和传输三处，文件服务作者仍可按收到请求的次序推理业务效果。

## 二、整体架构

启动后，shell 通过自己的挂载视图打开文件。管理任务在核 0 发布新版内存文件服务，核 1 上的客户端随即能打开新版，旧连接继续完成原来的请求。下图按调用方向给出三个运行路径。

```text
建立连接    shell → 私有挂载视图 → 本核目录副本 → 实例管理器 → 连接
传输数据    文件句柄 → 连接的请求队列 → 服务任务 → 文件内容或 UART
更新服务    管理任务 → 实例管理器 → 本核提交队列 → 有序日志
                                                    ├─ 核 0 重放 → 目录副本 0
                                                    └─ 核 1 重放 → 目录副本 1
```

以在控制台前接入计数服务为例，管理器先把已打开的串口句柄交给计数服务，再发布它的服务名。应用打开文件时经过第一条路径，拿到固定实例的连接；随后每次写入经过第二条路径，计数服务作为客户端再向串口服务发送一次请求。管理器发布新版计数服务时才经过第三条路径。两个目录副本各重放一次名称更新，UART 仍只接到一次文件写入。队列阻塞和唤醒都由任务运行时提供。

### 架构选择与代价

| 设计问题 | 决定及依据 | 维护成本与适用条件 |
| --- | --- | --- |
| 谁保护同一地址空间中的对象 | Rust 所有权控制对象生命周期，模块可见性限制构造入口。板级代码在启动时一次性分发内存、设备和发布权限。这样一次任务切换只更换执行上下文 | 内核镜像只接受同一工具链构建、依赖经过审查的组件。底层 `unsafe` 错误可影响整个镜像。服务的普通错误通过 `Result` 传播，内核 panic 按整机故障处理 |
| 哪一层允许替换 | 镜像保留两个服务实现，运行时切换服务实例。客户端依赖文件协议，实例拥有自己的任务、队列和业务状态。替换时只需要盘点一种入口和一组存活连接 | 首版能替换实现文件服务协议的组件。动态加载外部 crate、升级调度器和卸载代码页需要另行设计符号依赖、活动栈帧和跨版本类型布局 |
| 怎样组合文件服务 | 客户端的挂载视图负责命名，服务负责子树语义，本机通道负责交付请求。shell 通过改挂载就能把同一程序的输出转向另一项服务 | 每次打开文件要建立 fid，每次访问有请求与回复开销。协议只承担服务间操作。页帧分配、中断处理和调度继续使用本地 Rust 调用，启动过程因此能先于文件服务完成 |
| 哪些状态值得复制 | 两个核共享服务发现结果，查询频繁，发布操作少，目录更新可以用确定性的顺序函数表达。每核据此维护本地副本 | 写入增加日志与重放开销，慢副本限制日志回收。本地查询之后仍需为新连接取得实例引用。这个选择用于讲解一致性，性能收益需单独测量 |
| 为什么保留双核和抢占 | 阻塞的文件请求、跨核唤醒、并发发布都需要可观察的执行顺序。固定核调度使任务栈、就绪队列和副本的写入者明确 | 两个核之间可能负载不均。首版将任务指定到核上，使调度器、服务和复制层可以分别调试 |

### 模块与依赖方向

| 模块 | 持有的状态 | 对外接口与依赖 |
| --- | --- | --- |
| RV64 平台与内存 | 全局页表、页帧分配器、堆、每核启动栈、UART 寄存器 | 提供栈分配、时钟、核间唤醒和非阻塞串口收发。启动阶段完成内核及设备映射 |
| 任务运行时 | 每核当前任务、就绪队列、任务栈和等待状态 | 提供创建、让出、阻塞、唤醒和退出。任务固定到创建时指定的 hart，运行时只依赖平台与内存 |
| 本机传输 | 有界请求队列、在途请求、等待回复的任务 | 提供可克隆的发送端、唯一的接收端和一次性回复句柄。通过运行时阻塞和唤醒任务 |
| 文件客户端与命名空间 | 每个任务持有的挂载视图、连接、打开文件的位置 | 解析挂载点，将文件操作转换为请求。依赖服务查询接口和本机传输 |
| 服务发布与替换 | 服务实例、端点、版本号、连接计数和迁移状态 | 创建服务任务，发布和撤销名称，将连接固定到具体版本。实例管理器持有端点 |
| 节点复制 | 有序操作日志、各副本的目录和重放位置 | 为发布模块提供条件更新，为客户端提供一致查询。复制层只操作值类型的目录记录 |
| 服务与应用 | 串口输入队列、内存文件内容、shell 行缓冲等各自的状态 | 服务实现文件协议，应用通过挂载视图取得句柄。启动代码负责组装这些组件并分配所需权限 |

以下为目标源码布局。Cargo crate 提供需要独立编译或约束权限的边界。其余部分先使用私有 Rust 模块，避免每次修改内部数据结构都要调整跨 crate 接口。

```text
os/src/main.rs                  启动组装，选择模块版本并分发句柄
os/src/platform/                RV64 启动、时钟、IPI、UART 与异常入口
os/src/mm/                      全局页表、帧分配器、堆与任务栈槽
os/src/runtime/                 每核调度、等待、跨核通知和任务回收
os/src/transport/               请求队列、应答槽，对接 runtime 的等待接口
os/src/services/                实例管理、建立连接、服务生命周期
os/crates/service_api/          协议类型、客户端、挂载视图与安全端点接口
os/crates/registry/             顺序目录、操作日志和副本
os/components/                  shell、串口、内存、任务状态与计数服务
```

组件依赖 `service_api`。客户端按“挂载解析 → 连接接口 → 请求接口”发起调用。`services` 实现连接接口，同时使用 `registry` 查询身份、使用 `transport` 建立通道。`transport` 只依赖协议与运行时的等待接口，`runtime` 只依赖平台、内存和底层同步。`registry` 接收值类型的操作，在宿主环境也能执行。`main` 是唯一同时知道板卡、运行时和具体组件构造函数的模块。

以现有 `os/src/sync/mutex.rs` 为例，`Mutex::lock` 在竞争时直接调用 `current_task`、`WaitQueue::sleep` 和 `yield_task`。若调度器再使用这个锁维护就绪队列，启动和锁竞争都依赖调度器自身。新布局把关中断守卫和自旋锁放在运行时之下，把可休眠互斥锁放在运行时等待接口之上。服务实例管理器可以使用后者，中断入口和就绪队列只使用前者。

### 跨模块接口与所有权

以下是拟议的 Rust 签名。字段图给出所有权，调用图给出依赖方向。省略构造器、内部同步与方法体。

| 类型 | 最小状态 | 谁可以改变它 |
| --- | --- | --- |
| `Task` | `id, hart, state, stack: StackSlot, context: Context, entry: Option<Entry>` | 所属核的运行时。入口闭包只取一次，栈槽由调度器在任务退出并切走后归还 |
| `Namespace`、`FileHandle` | 前者持有共享的不可变挂载表。后者持有 `Arc<Connection>`、fid、打开模式和偏移 | 任务通过挂载操作取得新视图。普通读写借用 `&mut FileHandle`，按实际传输量推进偏移 |
| `Connection` | 连接号、固定版本的实例引用、发送端、按 tag 索引的应答槽 | 实例管理器授予连接，客户端分配 tag，回复和关闭竞争同一个应答槽的终态 |
| `Receiver`、`Reply` | 前者独占实例队列的接收权。后者持有一个具体请求的应答槽引用 | 服务任务移动请求负载并消耗回复句柄。两个类型均不可克隆 |
| `FileService` | 实现者独占文件或设备状态，以及按连接号、fid 索引的打开记录 | 实例任务依次把收到的请求交给同一实现。等待设备时，可以暂存请求的回复句柄 |
| `ServiceManager`、`Instance` | 管理器拥有实例表与发布权限。实例描述符持有版本、接入状态、发送端和任务标识 | 管理器启动、发布、替换和退役实例。服务任务持有实际业务数据 |
| `Registry`、`Directory` | 前者持有一个有界日志和两个副本。各副本持有顺序目录及已应用的日志位置 | 发布者提交条件更新。每个副本按序修改本核目录。目录的值仅含实例 ID 与版本 |

**运行时与服务端。** `Entry` 表示拥有启动参数的一次性闭包。平台组装代码可以把设备令牌移入闭包。运行时只负责调度闭包，文件服务通过队列接收请求。以下各组签名按所属类型列出。

```text
Runtime::spawn(&self, hart: HartId, entry: impl FnOnce() + Send + 'static)
    -> Result<TaskId, SpawnError>

Receiver::recv(&mut self) -> Result<(Request, Reply), Closed>
FileService::handle(&mut self, request: Request, reply: Reply)
Reply::send(self, result: Result<Response, FileError>) -> Result<(), Closed>
```

`Request` 带连接号、tag 和文件操作。以写操作为例，消息拥有 `Write { fid, offset, data: Box<[u8]> }`，成功结果为 `Written(usize)`。服务不持有发起请求的 `Task`。客户端提前关闭时，服务送回复可得到 `Closed`。写入已经交付且缺少回复时，客户端得到“写入结果未知”，不能据此自动重发。

**客户端与接入。** `Connector` 是管理器分发给客户端的只读接入句柄，只允许按服务名建立连接。传输发送端属于内部类型，普通组件通过 `Connection` 提交操作。接入句柄限定可连接的服务名，按组件的启动参数分发；挂载一段路径本身不授予新的接入权限。计数服务只接收打开的下游文件句柄。

```text
Namespace::mount(&self, prefix: AbsPath, name: ServiceName) -> Result<Namespace, MountError>
Namespace::open(&self, via: &Connector, path: &AbsPath, mode: OpenMode)
    -> Result<FileHandle, FileError>
Connector::connect(&self, name: &ServiceName) -> Result<Connection, ConnectError>
FileHandle::write(&mut self, data: Box<[u8]>) -> Result<usize, FileError>
FileHandle::close(self) -> Result<(), FileError>
Connection::call(&self, op: FileOp) -> Result<Response, FileError>
```

**发布与复制。** `Binding` 是可复制的 `(ServiceId, Generation)` 值。`Candidate` 是管理器准备的新实例句柄，不能用一个版本整数代替。管理器持有更新目录的权限。`replace` 消耗候选句柄，负责失败后的清理。静止迁移时，业务快照经管理通道从旧任务交给新任务，管理器不直接借用正在运行的服务对象。

```text
ServiceManager::replace(&self, name: &ServiceName, expected: Binding,
                        candidate: Candidate, mode: ReplaceMode) -> Result<Binding, ReplaceError>
Registry::submit(&self, change: Change) -> Result<(), PublishError>
Registry::lookup(&self, name: &ServiceName) -> Option<Binding>
Directory::apply(&mut self, change: &Change) -> Result<(), PublishError>
```

`Change` 包含服务名、期望的旧记录和目标记录。目标为空表示撤销；向空槽发布也携带观察到的槽版本。撤销后保留该版本，避免期间已有服务发布又撤销时，让过期请求意外成功。发起端在自己的副本应用对应条目后取得结果。`Directory::apply` 的输入和输出都可以在宿主测试中构造，无需实例表和任务调度器。

#### 所有权图

实线树枝表示持有。标有 `Arc` 的边延长目标寿命。标有 ID 的边只用于定位。服务入口开始运行后，接收端和业务对象由服务任务的栈或其拥有的堆对象承载。

```text
Runtime
 ├─ Task 表 ── Task ── StackSlot、Context、启动前的 Entry
 │              ├─ shell 任务运行期间 ── Namespace、FileHandle
 │              │                          └─ FileHandle ── Arc<Connection>
 │              └─ 服务任务运行期间 ── Receiver、FileService 实现、待完成的 Reply
 └─ 每核就绪队列 ── TaskId

ServiceManager
 ├─ 实例表 ── Arc<Instance> ── Sender、接入状态、TaskId
 └─ Registry ── 共享日志、两个副本 ── Directory ── Binding（ID 与版本）

Connection ── 实例引用、Sender、应答槽表
Sender 与 Receiver ── Arc<同一有界队列>
Reply ── 单个应答槽的引用
Namespace ── Arc<挂载表> ── 路径前缀与服务名
```

挂载表不延长任何实例的寿命。连接一直保留建连时的实例引用。在途请求还须计入退役条件，直到请求完成或取消。实例表在旧版本停止接入、连接与请求排空、服务任务退出后释放其引用。

#### 调用图

```text
启动    管理任务 → Runtime::spawn → 就绪队列 → task_start → 服务入口
打开    shell → Namespace::open → Connector::connect
                                      ├─ Registry::lookup → 本核 Directory
                                      └─ 实例管理器核对版本并取得连接引用
                 Namespace::open → Connection::call(Attach / Walk / Open)
写入    shell → FileHandle::write → Connection::call(Write) → 请求队列
        服务任务 → Receiver::recv → FileService::handle → Reply::send → 应答槽 → shell
替换    管理任务 → ServiceManager::replace → Registry::submit → 日志
        核 0、核 1 分别重放 → Directory::apply
```

查询结束与取得连接引用之间可能发生替换。实例管理器在服务名的接入锁内复核版本，成功后才授予引用。旧连接的 `write` 沿原发送端投递，直接到达旧服务。两个副本重放的 `apply` 只改变目录记录。

## 三、模块设计

### 平台与内存：建立共享执行环境

主核建立页表、堆及设备映射，再通过 SBI 启动从核。各核安装中断入口、切换到同一根页表并建立本地调度队列。主核等待两个核就绪，创建管理任务。管理任务按依赖顺序启动服务，收到就绪通知后发布其名称。最后，启动代码为 shell 建立挂载视图，将 shell 加入就绪队列。两个任务状态服务分别固定在其观察的核上，计数服务由需要组合输出的清单项创建。早期启动信息使用独立的调试输出。运行期应用输出经过文件服务。

主核在开放启动屏障前写完页表根、各核控制块及启动栈，使用 release 发布就绪状态。从核以 acquire 观察该状态，设置自己的 `tp`、`satp`、`stvec` 和时钟后才确认在线。在线确认表示该核已经能接收调度通知。当前 `secondary_start` 先置在线位，随后才安装最终页表和时钟。阶段 1 将在线确认移到这些步骤之后。目录副本与服务端点都建立后，shell 才能运行。任何一步失败，启动代码通过早期调试口报告最后成功的步骤及 hart ID。[现有从核启动顺序](https://github.com/comix-kernel/comix/blob/e2dc94bcb05d85e5748a2717af8d87714195eae1/os/src/arch/riscv/boot/mod.rs#L75)

启动分配器保留固件、内核映像、DTB 和页表占用的物理区间。页表对代码段设为可读可执行，对只读数据设为只读，对堆和栈设为可读写且不可执行。首版预映射有限数量的任务栈槽，栈边界保留无映射保护页。内存模块拥有底层页帧，任务独占一个栈槽。回收任务时归还栈槽，耗尽时 `spawn` 返回资源不足。固定映射使栈的常规创建和销毁无需跨核刷新 TLB，代价是最大并发任务数受启动配置限制。

### 任务运行时：在同一特权级执行与抢占

应用和服务以同一工具链构建为 `no_std` Rust crate，静态链接进教学镜像。运行时接受持有入口和参数的可执行任务，例如 `spawn(hart, entry)`。跨核移交的入口满足 `Send + 'static`。shell 和服务 crate 使用 `#![forbid(unsafe_code)]`，只依赖安全接口。启动代码把不可复制的设备令牌交给对应驱动，把目录发布权限交给管理任务，普通任务只取得挂载视图与端点。平台层封装 CSR、汇编和 MMIO，裸指针访问集中在可信底层。内存、同步、切换代码分别维护其安全条件。同一 S 态下，组件之间的访问约束由编译器、受控依赖和可信底层实现共同维持。

运行时采用固定核的时间片轮转。时钟中断保存被打断任务的完整整数寄存器和返回状态，普通函数调用边界的上下文切换保存 `ra/sp/s0–s11`。首版构建为所有任务禁用浮点和向量指令，并检查反汇编结果。任务退出时先切换到调度器栈，由调度器回收已退出任务的栈。每核就绪队列和中断寄存器属于该核。跨核唤醒只提交一次就绪通知并按需发送 IPI。运行时在持有自旋锁或关闭抢占时推迟任务切换。

#### 任务状态与等待责任

调度器区分 `Ready`、`Running`、`Blocked(wait_id)` 和 `Exited`。每核调度器独占本核就绪队列。其他核只能发送带任务身份和等待序号的唤醒通知。等待序号每次阻塞都更新，旧通知即使延迟到达也不能把下一次等待误判为完成。

| 转换 | 写入者和时机 | 资源约束 |
| --- | --- | --- |
| 创建 → Ready → Running | 运行时取得栈槽、建立入口上下文，所属核入队并选择运行 | 栈槽申请或初始化失败时释放已取得资源，任务发布前调度器看不到它 |
| Running → Ready | 当前核在允许抢占的时钟中断返回点保存上下文 | 同一任务最多占用一个队列位置，切换代码运行时持有的守卫不得留在旧任务栈上阻碍新任务 |
| Running → Blocked → Ready | 当前任务登记等待，所属核运行时完成切走。事件源发布唤醒后由所属核恢复就绪 | 若事件早于切走，任务消费待处理标记继续执行。若事件晚于切走，所属核核对等待序号后入队 |
| Running → Exited | 任务入口返回运行时包装函数，包装函数释放组件上下文后交回 CPU | 调度器在自己的栈上回收任务栈槽，失效的任务标识不得指向复用该槽的新任务 |

中断上下文的工作限于重设定时器、记录有界事件、设置调度标记和发送必要的通知。核间中断只提示所属核查看待办项。任务上下文负责分配消息、执行服务逻辑、推进副本和等待队列容量。若串口输入环已满，驱动保留已接收的字节并记录溢出次数，调试输出走独立路径，避免错误处理再次进入出错服务。

### 文件客户端与命名空间：解析对象并取得句柄

任务创建时继承父任务的挂载视图。一次挂载修改产生新视图，由调用任务持有。挂载项记录“本地路径前缀 → 已发布的服务名”。`open("/dev/cons")` 先按完整路径分量选择最长挂载前缀，再查询服务名的当前版本，通过该版本的端点建立连接。已有连接继续引用建立时的实例。服务端只遍历自己导出的子树。首版支持绝对路径、目录遍历和精确覆盖挂载点。同一目录的合并挂载留待扩展。

本机协议使用带类型的 Rust 消息。每个连接单独分配文件标识 `fid` 和请求标识 `tag`。服务端将 `fid` 映射到树中的节点和打开模式，客户端将 `tag` 映射到待完成请求。

| 操作 | 服务端语义 |
| --- | --- |
| `Attach`、`Walk` | Attach 建立根 fid。Walk 从现有 fid 按名称遍历，为目标分配新 fid。遍历失败时保留原 fid |
| `Open`、`Read`、`Write` | 检查打开模式。普通文件按请求中的偏移访问，客户端按实际传输字节数推进位置。控制台按字节流读写 |
| `Clunk`、连接关闭 | Clunk 释放一个 fid。连接关闭时批量释放剩余 fid，并以关闭错误结束待回复请求 |

### 本机传输：交付请求并唤醒等待者

请求队列同时限制条目数和负载字节数。超出单条上限的请求直接返回错误。队列已满时发送者等待容量。发送操作把字节缓冲区的所有权移交给队列，只读负载也可以共享。服务端通过按值接收回复句柄的 `Reply::send(self, result)` 完成请求，丢弃未完成的回复句柄会唤醒调用者，传输层依据交付状态返回关闭或写入结果未知。客户端用 `tag` 匹配乱序回复。同一连接在请求完成前保留该 tag。

队列在同一把锁下检查条件、登记等待者并设置等待状态。生产者在锁下取走等待者，释放队列锁后通知其所属核。运行时在真正切走任务前检查唤醒标记，处理“登记完成后、切换之前”到达的通知。串口接收用 `try_read` 有界轮询并向服务任务发出就绪通知。服务任务负责交付字节，shell 负责行编辑与回显。

#### 一次跨核文件写入

设核 1 上的 shell 首次写入 `/dev/cons`，串口服务运行在核 0。挂载视图将 `/dev` 关联到服务名 `console`，服务根目录包含 `cons`。

1. 客户端按路径分量解析挂载视图，从核 1 的目录副本取得 `console` 的实例身份。实例管理器核对版本并获得连接引用。若这期间发生替换，客户端在发送任何文件请求前重新查找。
2. 客户端依次发送 `Attach`、`Walk("cons")` 和 `Open(Write)`。服务在连接私有的 fid 表里建立记录。返回的文件句柄拥有连接引用和 fid。不同连接可以使用相同的 fid 数值。
3. 客户端为 `Write` 保留应答槽，把字节缓冲区移入请求。队列接收请求后才向服务核发送通知。服务取走请求、释放队列锁、检查 fid 权限，最后交给 UART 驱动。硬件暂不可写时，服务保留未完成的字节及回复句柄，留出 CPU 给其他任务。
4. 服务返回实际写入的长度。客户端完成对应 tag，释放应答槽。连续写同一个普通文件句柄时，客户端串行推进偏移。显式偏移的请求可同时在途。之后的读写复用已有连接，目录替换不会改变这个 fid 的目标。
5. 显式关闭发送 `Clunk`，允许调用者等待结果。最后一个连接句柄析构时设置关闭标记并通知服务，由服务统一释放未关闭的 fid。析构路径不等待满队列中的空位。连接关闭与正常回复竞争同一应答槽，应答槽只能从等待态进入一个终态。连接号与请求序号共同标识应答槽，迟到的旧回复不能完成新请求。关闭时唤醒等待容量、数据及回复的三类任务。

接口区分 `NotFound`、`PermissionDenied`、`Busy`、`Closed`、`NoCapacity` 和 `WriteOutcomeUnknown`。客户端报告挂载解析错误，服务端报告子树查找或权限错误。fid、tag 或单请求负载超过上限时，分配方在登记请求前返回错误。若关闭方在队列锁内成功摘除尚未取走的写请求，返回 Closed。服务已取走的写可能已经影响设备，断连且缺少确认时调用者收到“写入结果未知”。客户端只自动重试尚未发送请求的版本查找。服务端把设备结果回复一次，复制层也不持有重发设备操作的入口。

### 实例管理器：接入、替换和业务状态迁移

启动清单把各服务构造函数适配到统一工厂入口。编译器检查构造参数和端点类型，服务实现负责校验快照的模式版本和内容。每个工厂声明所实现的服务契约与版本。服务名在启动清单中约定所需契约（如可写字节流），管理器在发布前检查候选的声明及导入结果。声明相符后的实际语义由同一组契约用例检验。两个实现可以同时链接、创建独立实例并在运行时切换。服务名用于发现，`(ServiceId, Generation)` 标识一次实例发布，连接持有该实例的引用。每个服务独占自己的 fid 表与业务状态。首版替换回收任务、队列与数据。两个实现的机器码驻留镜像。动态装入任意 ELF crate、修补调用点和卸载代码页属于后续的装载器课题。

1. **并存切换。** 管理器先启动新版并等待就绪，再按预期旧版本更新服务目录。新连接解析到新版。旧连接和在途请求由旧版完成。最后一个旧连接关闭后，管理器排空队列、停止旧任务并回收实例。新版本就绪失败或版本条件不匹配时，管理器销毁候选实例，保留当前发布。
2. **带状态迁移。** 管理器先关闭旧实例的新连接入口。若仍有连接或在途请求，恢复入口并返回 `Busy`。旧实例在静止状态生成有版本号的快照，候选实例校验并导入。导入成功后才发布新版。校验或发布失败时恢复旧实例接入。教学样例在两个内存文件模块之间迁移内容与修订号，串口驱动继续持有 UART 令牌。

客户端取得目录中的版本后向实例管理器申请该版本的连接引用。每个服务名有独立的可阻塞互斥锁。管理器在锁内检查实例是否仍接收连接并增加计数。退役版本拒绝新接入，客户端重新查询。切换时管理器在同一把接入锁下提交版本更新，标记旧实例退役，再开放新实例接入。处理文件请求、等待回复和导入快照均在锁外完成。迁移期间到达的新连接收到可重试的忙错误。

#### 替换期间可观察的状态

实例依次经历 `Starting → Active → Draining → Retired`。`Starting` 实例可以分配队列、验证协议版本并导入快照。管理器在目录更新成功并开放接入后才把它交给新客户端。`Draining` 实例继续服务已固定版本的连接。停止实例的条件包括连接数为零、在途请求为零、挂起的设备完成回调已撤销或返回，服务任务也已交回执行权。实例表最终释放端点引用。

并存切换适用于无状态服务或业务上允许两份状态独立演进的服务。例如旧版和新版分别消费自己的记录文件。若两个客户端必须看到同一份可写文件，管理器采用静止迁移。并存切换无法自动合并两份文件的修改。快照定义独立的模式版本，记录业务字段与修订号。fid、tag、队列地址、栈指针和硬件令牌只在来源实例有效，迁移代码逐字段重建业务状态。

管理任务按名称串行化发布和迁移命令。耗时的就绪检查和快照导入允许其他名字继续服务。撤销与再次发布使用单调代号，序号耗尽时返回资源错误。并发测试在三个位置分别设置屏障，即读出旧版本之后、目录更新之前和最后一个旧连接关闭之前。各用例检查请求实际到达的实例、返回值和回收计数。

### 服务目录：按同一顺序更新本核副本

第一个复制对象是服务目录。教学配置在同一 QEMU 机器的两个 hart 上各放一份目录，展示 NrOS 在 NUMA 节点间复制状态的执行规则。任务私有挂载视图决定路径指向哪个服务名，复制目录决定该名字当前对应哪个实例。端点表负责把实例身份转换为可用连接。

| 操作 | 执行位置与结果 |
| --- | --- |
| 发布、替换、撤销 | 写请求携带名称、预期版本和新记录。各核把请求放入本地提交队列，合并者收集一批请求，按序追加到共享日志。副本逐条执行版本比较和更新，发起者在本地执行到该条目后取得结果 |
| 查询 | 采样已发布的日志末端，本地副本至少重放至该位置，再读取本地目录。若核 0 的发布已经返回，核 1 随后开始的查询须能观察到该发布或更新的版本 |
| 回收日志 | 每个副本公布已应用的位置。有界环形日志以最慢副本的位置为回收界限。日志满时写入者请求落后核推进并等待容量。等待期间释放日志锁。空闲核也处理推进通知 |

#### 顺序规格与提交顺序

目录核心可以写成两个普通函数。`apply(&mut Directory, Change)` 执行条件更新，`lookup(&Directory, Name)` 返回一个可复制的身份值。管理器为启动清单中的名称预留目录槽。插入要求空槽及其版本与预期相符，替换和撤销要求实例与槽版本均符合预期，每次成功更新使该槽版本加一。版本冲突与容量耗尽都产生确定的错误结果，占用日志位置并推进游标。名称、候选实例 ID 和预期版本在提交前确定。`apply` 内部只访问副本自有的数据，禁止读取时钟、分配外部 ID、查端点、唤醒任务或访问设备。顺序目录因此能直接作为差分测试的参照实现。

日志维护三个量。`tail` 表示已完整发布的连续前缀末端，`applied[h]` 表示核 h 已执行的前缀末端，最小的 `applied` 决定可复用的日志槽。首版用短锁串行追加批次，先填入所有记录，再以 release 顺序公布 `tail`。副本以 acquire 顺序读取位置，按序更新本地目录，再公布 `applied[h]`。单调序号和环形槽下标分别保存，便于区分两次回绕。每个副本只有一个执行更新的上下文。多个本地请求可以共享一次合并操作。

写调用在发起端副本执行过相应记录后取得结果。查询开始时采样 `tail`，等本地副本执行到该位置后，在本地读保护下取值。选择已发布前缀作为读取下界，可以避免某个读者已经见到新版本、稍后的读者却从落后副本读回旧值。代价是查询偶尔会等待一笔尚未向写入者返回的更新。已打开文件上的数据传输绕过目录，因而不承担这一成本。

例如两个核都按 A/7 提交变更，分别希望接入 B 和 C，日志先记录指向 C 的操作。两个副本都先把 A/7 改为 C/8，随后都对预期值为 A/7 的另一项返回冲突。每个提交者只从发起端取得一次结果。若日志容量为 4，两个游标分别为 12 和 9，序号 10 至 12 仍需保留。追加 13 后，提交 14 的任务必须等待慢副本至少应用序号 10。执行重放的任务独立于服务接入锁和业务请求队列。日志满时仍可运行。首版假设两个 hart 持续在线，运行中失去一个副本时停止验收并输出游标。

### 服务组件与应用：导出对象、组合服务

首版用三类文件检验同一个协议。内存文件的状态由服务拥有，串口文件把读写交给设备，任务状态文件则从调度器取得一个只读视图。组件只获得完成这项工作所需的句柄。shell 使用相同的打开、读写和关闭操作；具体连接关系由启动清单给出。

| 导出路径示例 | 服务持有的资源 | 一次文件操作的效果 |
| --- | --- | --- |
| `/work/note` | 内存服务独占文件字节和修订号 | 按偏移读写；成功写入返回实际长度并更新修订号。静止迁移时两者一起转移 |
| `/dev/cons` | 串口服务持有唯一 UART 令牌，保存尚待完成的读写 | 字节流读写。无输入时暂存读请求，继续处理就绪事件；一次发送只提交已准备好的字节 |
| `/tasks/0/<id>/status` | 核 0 上的状态服务持有本核运行时授予的只读查询接口；核 1 同理 | 以只读模式打开时按带代号的任务 ID 采样；后续分段读取同一份文本，读到末尾返回零 |

**任务对象。** 启动时分别将两个状态服务挂到 `/tasks/0` 和 `/tasks/1`。每核服务与被观察的运行队列在同一核执行。查询接口由组装层传入，其返回类型只含值字段；运行时先检查调用核与授权 hart 一致，再在本核短临界区核对槽号和代号，复制任务 ID、所属核和调度状态，退出临界区后由服务格式化并存入当前 fid。任务在 Walk 与 Open 之间退出则 Open 返回 `NotFound`；成功打开后即使槽位复用，读者仍能读完原快照。Clunk 释放快照，打开数量受 fid 配额约束。现有 Comix 的状态生成器取得任务弱引用并锁住任务，还可能进入地址空间统计；教学接口只返回上述三个值，状态服务借此与调度器内部类型解耦。[现有状态生成器](https://github.com/comix-kernel/comix/blob/e2dc94bcb05d85e5748a2717af8d87714195eae1/os/src/fs/proc/generators/process/status.rs#L22)

**组合示例。** 管理器先取得串口的可写句柄，把它作为构造参数移给计数服务。后者导出可写的 `cons` 和只读的 `count`。将它挂到某个任务的 `/out`，该任务写 `/out/cons` 时，计数服务将缓冲区交给下游，收到 `Written(n)` 后才累加 n 并向上游回复 n。写入四字节而下游确认两字节时，调用者得到 2，读 `/out/count` 也只增加 2。若交付后断连，返回 `WriteOutcomeUnknown`，计数保留已确认值；这时发起者无法从计数推断硬件已经发出的字节。换成有相同写入约定的记录服务，可用同一程序检验整条链。计数达到上限时，对非空写入在转发前返回容量错误；接近上限时最多转发剩余可计数的字节。

组装按依赖顺序进行，每层接收已打开的下游句柄；计数组件只获得这个句柄，无权自行查找其他后端。每个同步调用都指向先启动的下游服务，因此该清单不会形成相互等待的环。转发期间释放传输锁，计数服务作为普通任务等待下游回复；串口服务和目录推进任务仍可运行。换绑下游名称后，计数服务持有的旧连接继续生效。需要让新流量走新版后端时，用新句柄构造另一计数实例，再切换上游绑定。若计数必须连续，按静止迁移的规则复制已确认总数。UART 令牌始终在设备服务中。

### 跨模块同步约束

| 同步范围 | 保护的操作 | 等待与释放顺序 |
| --- | --- | --- |
| 本核运行队列与唤醒标记 | 时间片到期、任务就绪、等待序号匹配 | 本核屏蔽中断完成短更新。跨核发送者写入通知并发送 IPI，所属核自行入队 |
| 传输队列与应答槽 | 登记等待者、请求交付、完成或关闭的竞争 | 队列锁内登记或摘除等待项。锁外通知与切换。阻塞时保留任务和应答槽身份，释放队列锁 |
| 服务名接入锁 | 获取版本引用、关闭接入、提交新版本 | 发布者可持此可休眠锁等待日志空间。副本推进路径不能取得接入锁。文件服务函数、快照函数和完成回调始终在锁外执行 |
| 复制日志与本地目录 | 批次提交、重放、发布游标 | 复制层在日志锁内预留或发布槽位，释放锁后执行顺序更新。慢副本应用完成前不得覆盖对应记录，应答和调度通知放在副本更新之后 |

## 四、维护与演进

### 需要保持稳定的契约

| 契约及维护位置 | 允许的内部改动 | 改动如何验收 |
| --- | --- | --- |
| `service_api` 的路径、请求、错误、短读写和关闭语义 | 服务可更换目录结构、缓存和设备实现。公共枚举新增操作时，同一镜像里的客户端和服务一起重新编译 | 同一套协议契约用例分别驱动内存服务两个版本。使用编译穷尽匹配定位需要处理新增操作的代码 |
| 服务构造入口和快照格式 | 构造函数取得明确授权的端点与资源。业务快照字段独立于内部 Rust 结构布局，模式升级由目标实现负责读取旧格式 | 保存一个旧模式的最小快照测试样本，验证数据与修订号。未知模式、损坏样本和不足容量都在目录提交前返回错误 |
| `registry` 的顺序语义 | 可更换哈希表、日志容量或批量大小。日志序号和对外服务版本分别演进 | 对同一份并发请求历史保存提交顺序，比对单副本及双副本的返回值、最终键值和游标。调整批量大小后重复运行 |
| `runtime` 的创建、等待和通知语义 | 可改就绪队列容器及时间片长度。服务与传输仅持有等待标识和唤醒接口 | 在宿主等待模型中覆盖提前唤醒、迟到通知和重复通知，然后用双核 QEMU 验证真实中断与栈切换 |
| RV64 上下文和内存所有权 | 汇编只读取约定布局的上下文。栈槽、页表页及 MMIO 区域各有唯一所有者 | 在 Rust 侧断言汇编字段偏移和栈对齐，检查 ELF 段权限、保护页、定时抢占及任务回收。修改中断入口时同时运行双 hart 压力用例 |

静态链接使公共 Rust 接口的变更可以在一次构建中检查完。跨构建仍需兼容的是明确保存的业务快照及供教学脚本使用的协议行为。新增抽象要有具体使用者。例如 UART 服务和内存服务已经需要相同的请求入口，而页表只有一个 Sv39 实现，保留具体类型即可。只有在需要独立编译、限制权限或替换实现时，才增设 crate 边界。

### 典型改动的影响范围

- **新增时钟文件服务。** 在 `components` 实现只读子树，通过构造参数取得只读时钟句柄，在启动清单中发布。使用同一客户端测试路径解析、读和写入拒绝。若必须在路径解析器里判断文件名 `time`，说明设备知识已经进入客户端。
- **升级内存服务的存储格式。** 在目标服务中增加旧快照解码和校验。目录只发布新的实例身份。先让旧连接执行完毕，再验证升级前后的字节内容和修订号。若需要把快照放进复制日志，说明业务状态和服务发现没有分开。
- **把 UART 轮询改为外设中断。** 改动板级中断入口、驱动和硬件通知适配。传输层仍接收相同的就绪事件，协议和行编辑逻辑沿用原测试。额外验收中断风暴、队列满和中断到达后任务能否及时恢复。
- **调整日志容量。** 修改复制模块的配置，同时跑容量 1、4 和默认值的回绕测试。若文件服务需要持有日志锁才能继续响应已连接客户端，说明数据读写错误地依赖了发现路径。

### 定位故障与核查依赖

调试构建在每个 hart 上预留固定长度事件缓冲。任务事件带 `hart/task/wait_id`，文件请求带 `connection/tag/generation`，目录更新带 `log_seq/applied`。记录位置放在状态转换处。写满时覆盖旧项并累计覆盖次数。异常处理通过早期调试口读取最近事件，避开文件服务。这样可以关联一次文件操作及其服务版本，也能看到任务停在队列、接入锁还是日志容量上。正常镜像可以关闭事件记录。

| 故障表现 | 先核对的数据 | 最小复现场景 |
| --- | --- | --- |
| 客户端挂起，队列仍有请求 | 队列的等待序号、所属核收到的通知、任务是否已入队 | 服务登记等待后暂停，另一核入队并唤醒，再允许服务切换 |
| 替换成功后新连接仍进入旧实例 | 查询采样的 tail、读取副本游标、接入时重新核对的代号 | 在旧查询返回后暂停客户端，完成替换，再恢复接入 |
| 写入设备后输出重复 | 连接与 tag、服务实际写入次数、重放位置 | 让另一核滞后数条日志，执行一次设备写再追赶 |
| 停止客户端后旧实例仍不能回收 | 活跃连接、未完成回复、驱动回调及服务任务状态 | 队列已满时关闭最后连接，检查非阻塞关闭标记是否被消费 |

CI 从 `cargo metadata` 检查依赖方向，禁止应用直接依赖板级驱动、实例管理器或复制内部实现。宿主测试编译 `service_api` 与 `registry`，双核 QEMU 执行跨层用例。变更 `unsafe` 边界时，在相关实现旁维护地址来源、访问权和有效期三项约束。审查同步改动时核对上节的锁顺序和唤醒用例。验收脚本、契约测试和调试事件使用相同的标识，文档只记录语义与定位入口，不逐项复制函数签名。

基线的 `os/src` 共有 380 个 Rust、汇编和链接脚本文件，`cloc --skip-uniqueness os/src` 统计为 47,867 行有效代码，含内嵌测试。最终预算建议为 **8,000 行自有运行代码**，包括平台、任务、传输、协议、复制、服务和演示应用。测试放在独立目录并单列行数，构建脚本、文档和第三方依赖分别列项。移入其他 crate 的自有实现仍计入总额。阶段 4 根据实测行数调整各模块预算，优先裁去额外的命令、协议扩展和重复适配。

### 迁移顺序与规模控制

阶段 1–2 以独立构建目标替换启动、页表和任务模型。先隔离旧的 `build.rs` 制盘逻辑和默认 feature，再引入新的任务入口。原有内核的 Linux 任务结构、用户 ELF 和磁盘根系统作为一组退出调用路径。只要新任务仍通过旧 `current_task` 取得 fd 或信号状态，这组代码就尚未达到删除条件。

阶段 3 的传输与阶段 5 的顺序目录可分别在宿主环境开发，两者在各自的验收阶段接入 QEMU。阶段 4 先用单份目录固定协议与命名空间语义，阶段 5 在同一查询接口后接入复制，阶段 6 再引入多版本接入。这样同一个打开文件测试依次覆盖三个集成节点，首次失败的位置能区分协议、复制和替换问题。最终删除被取代的构建入口，同时更新根 README、依赖清单与 CI，旧版功能通过基线提交追溯。

8,000 行作为首版设计预算，初步分配为平台与内存 1,800 行、任务与同步 1,500 行、传输与协议 1,400 行、命名空间与实例管理 1,100 行、目录复制 1,000 行、组件与启动组装 1,200 行。按每段代码的主要职责归集一次。阶段 2、4、6 分别记录实际值和超支原因。若某层超支，先检查是否重复实现了相邻层的状态或增加了首版之外的接口，再决定调整哪一项预算。

## 六、实施阶段与验收

`make check-teaching STAGE=N` 是拟新增的统一入口，阶段 1 实现驱动，后续阶段依次以前一阶段通过为前提。驱动执行该阶段及其前置阶段的检查。宿主用例通过同步屏障控制并发顺序，QEMU 用例通过串口和内核计数核对执行结果。遇到断言失败、超时、核数不足或缺少预期输出时，驱动返回非零退出码。

### 阶段 1　无盘双核启动

新建独立的教学构建入口，链接最小模块集。执行 `make check-teaching STAGE=1`，驱动以 `-machine virt -m 128M -smp 2 -bios default -net none` 启动 QEMU，只连接串口。

串口须报告两个不同的 hart ID、同一根页表物理页号，以及各核至少一次时钟中断。移走磁盘镜像、撤去 mkfs 工具后重新构建并冷启动仍应通过。当前从核初始化失败会退回单核，教学验收将退回视为失败。

### 阶段 2　同特权级 Rust 任务

创建三个任务，两个固定在同一 hart 忙循环，第三个固定在另一 hart。当两个忙循环均未主动让出 CPU 时，每个任务的计数都必须增长。记录任务切换前后的根页表页号和中断入口保存的 SPP，确认所有任务使用同一根页表，时钟中断均来自 S 态。

另行循环创建、退出并回收 100 个任务，最终空闲栈槽数回到初始值。填满栈槽后再创建任务应返回资源不足，释放一个槽后可以再次创建。编译失败用例验证普通组件无法构造第二份 UART 令牌或调用裸 MMIO 接口。

### 阶段 3　请求、回复与阻塞

用一个回声服务在两个 hart 间传递请求缓冲区。宿主测试强制在“登记前、已登记未切走、已阻塞”三个时刻送达消息，每次恰有一个完成结果。

限制队列为两个请求，第三个发送者先等待，服务取走一个请求后恢复。服务端逆序回复两个 tag，客户端仍取得各自结果。关闭接收端或丢弃回复句柄时，等待者都收到与交付状态匹配的错误。另设设备写已执行、应答尚未返回的断连点，调用者收到结果未知，设备计数只增加一次。编译失败用例覆盖复制接收端和重复发送同一回复。

### 阶段 4　文件服务与任务命名空间

先用单份目录运行内存服务、UART 服务和 shell。两个任务各自把 `/dev/cons` 挂到不同服务，用相同代码写入不同标记。一个标记只能出现在串口，另一个只能出现在内存文件中。

依次验证只读打开后写入失败、`Walk` 失败后原 fid 可用、`Clunk` 后访问失败、断开连接后服务端 fid 数回到基线。让一个任务等待键盘输入，另一个任务须在输入到达前完成文件读写，键入字符只回显一次。

任务状态用例先打开一个任务的 status，读取前半段后让该任务退出并复用其槽位，再读取剩余字节，拼接结果应属于同一次采样。用旧 ID 重新打开应得到 `NotFound`。组合用例给计数服务接入一个可控制短写和断连的下游，核对上游结果、确认字节数及下游实际收到的请求次数。相同客户端换接 UART 后再用串口输出校验。

### 阶段 5　双核复制目录

记录合并后的日志，用顺序目录回放并计算期望结果，逐项核对两个副本的结果和状态。预先排入多个不同服务名的写请求，确认一次合并能提交多条记录，每名提交者收到自己的应答。QEMU 中让核 0 的发布调用返回后再通知核 1 查询，核 1 须读到新版本。让两名发布者同时用同一旧版本条件提交替换，恰有一方成功。

将环形日志容量设为 4，暂停一个副本，填满日志后再次提交，检查写入者等待、最旧条目仍在。恢复副本后继续提交至少 16 次，验证回绕、两个游标追平及最终状态。再令一个查询先观察已追加、尚未向发起端应答的更新，随后从另一核查询同一名称，验证版本不会倒退。一次串口写入同时记录请求数和输出字节数，副本追赶期间每个请求只产生一份预期字节序列。

### 阶段 6　运行时替换与最终裁剪

shell 保留旧连接，管理任务切换到新版，另一核通过同一挂载路径新建连接。旧连接完成旧版请求，新连接读到新版标识。释放旧连接后，旧任务、队列、fid 和在途请求计数全部归零。

迁移用例先保留一个打开的内存文件句柄，管理任务应收到 `Busy`。关闭句柄后重试，比较迁移前后的文件内容与修订号。另起一轮，在校验时注入失败，确认原版本仍可接收新连接且文件内容完整。

最后从干净检出执行 `make run` 和完整验收，检查 Cargo 依赖树、实际编译的模块和源码计数。默认镜像须直接进入服务 shell。依赖检查须确认组件仅通过公开接口访问内核。按第五节的口径列出各模块行数，超出预算的项目注明原因。
